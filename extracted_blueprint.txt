1.2 Strategic Synthesis: Kaizentrix Platform vs. Market Benchmarks
The Kaizentrix Enterprise Teleconsultation Platform balances clinical safety, enterprise scalability, and commercial viability by borrowing proven strengths from market leaders while deliberately avoiding their operational vulnerabilities:
Practo Archetype (Marketplace & SaaS): Adopt the fluid doctor discovery, calendar slot management, and provider booking ergonomics; reject open unverified doctor marketplaces and aggressive monetization cross-sells.
Apollo 24|7 Archetype (Hospital Omnichannel): Adopt strict clinical governance, structured documentation, and high-availability enterprise resilience; reject heavy operational dependencies on physical pharmacy supply chains and unvalidated autonomous AI clinical triage in early phases.
eSanjeevani Archetype (Public Infrastructure): Adopt standards-based interoperability (ABDM M1/M2/M3, SNOMED CT/ICD-10 readiness), robust virtual waiting rooms, and low-bandwidth WebRTC resiliency; reject cumbersome government bureaucracy and UI friction.

2.1 Business Requirements (BUS)
BRD-BUS-01 (Safe Core MVP Focus): The platform must establish a secure, reliable teleconsultation core rather than attempting to replace an entire Hospital Information System (HIS) or Electronic Health Record (EHR) ERP in the initial release.
BRD-BUS-02 (Booking Conversion Rate): The booking funnel must achieve $\ge 95\%$ successful completion for valid booking attempts.
BRD-BUS-03 (Consultation Reliability): The video consultation subsystem must deliver a $\ge 98\%$ join success rate across supported devices and network conditions.
BRD-BUS-04 (High Availability): Core booking and consultation services must sustain 99.9% monthly availability (excluding agreed planned maintenance).
BRD-BUS-05 (Enterprise Auditability): 100% of privileged access, administrative overrides, and sensitive clinical record accesses must be immutably logged and auditable.
BRD-BUS-06 (Controlled Phased Delivery): Delivery must follow a structured 20–28 week timeline spanning Discovery, Architecture, MVP Build, Integration/Testing, and a Controlled Pilot.
2.2 Functional Requirements (FUN)
BRD-FUN-01 (Patient Identity & CIAM): Support patient registration, login (phone/email/federated), profile management, and explicit legal consent capture/versioning.
BRD-FUN-02 (Provider Directory & Search): Public and authenticated directory of clinicians searchable and filterable by specialty, clinic affiliation, languages spoken, consultation fees, and availability slots.
BRD-FUN-03 (Appointment Scheduling Engine): Support appointment search, real-time slot reservation with concurrency protection, booking confirmation, rescheduling, cancellation, and basic no-show tracking.
BRD-FUN-04 (Virtual Waiting Room & Join Checks): Provide a digital waiting room for patients with hardware pre-call diagnostics (camera, mic, network speed) and clinician admittance controls.
BRD-FUN-05 (Managed WebRTC Teleconsultation): Secure, low-latency audio/video streaming via a managed WebRTC service provider with in-session controls (mute, camera toggle, screen sharing, device switching) and dynamic network adaptation.
BRD-FUN-06 (Patient Intake & Context Review): Capture pre-consultation intake forms and medical history submitted by the patient, accessible to the attending clinician before admitting the patient.
BRD-FUN-07 (Encounter Documentation & Notes): Enable clinicians to document subjective/objective clinical notes, diagnoses, and consultation summaries during or immediately after the session.
BRD-FUN-08 (Digital Prescription / Advice Workflow): Provide a structured prescription builder (medication, dosage, frequency, duration, instructions) subject to jurisdictional and clinical validation, lockable with digital sign-off.
BRD-FUN-09 (Secure Medical Attachment Exchange): Allow patients and clinicians to upload and view clinical documents/images with strict allowlist file type validation, size limits, and asynchronous malware scanning.
BRD-FUN-10 (Multi-Channel Notifications): Automated transactional dispatch of booking confirmations, calendar invites, and join reminders via SMS, Email, and Push notifications without exposing sensitive health information in message bodies.
BRD-FUN-11 (Payment Integration & Financial Tracking): Integration with a compliant payment gateway for slot fee collection, supporting refunds, cancellations, and itemized transaction receipts.
BRD-FUN-12 (Clinic & Platform Admin Console): Administrative tools to manage clinician onboarding, credentials, roster availability, service catalogs, appointment overrides, and operational metrics.
2.3 Non-Functional Requirements (NFR)
BRD-NFR-01 (API Response Latency): 95th percentile ($p95$) API latency $< 500\text{ ms}$ for standard transactional endpoints under agreed load.
BRD-NFR-02 (Scalability & Concurrency): Architecture must support horizontal auto-scaling and pass load testing at $2\times$ forecast peak concurrent bookings and sessions.
BRD-NFR-03 (Disaster Recovery & Data Resilience): Recovery Time Objective ($\text{RTO}$) $\le 4\text{ hours}$; Recovery Point Objective ($\text{RPO}$) $\le 15\text{ minutes}$ for transactional databases.
BRD-NFR-04 (Frontend Accessibility): User interfaces across patient and clinician portals must comply with WCAG 2.2 Level AA standards.
BRD-NFR-05 (Localization & Timezone Consistency): Database storage in UTC; localized presentation of dates, times, currencies, and multi-timezone scheduling.
2.4 Security & Privacy Requirements (SEC)
BRD-SEC-01 (Zero Trust Network & Ingress): Perimeter protected by WAF, DDoS protection, TLS 1.3 in transit, and private isolated database/storage endpoints.
BRD-SEC-02 (Mandatory Workforce MFA): Multi-Factor Authentication (MFA) strictly enforced for all clinicians, clinic administrators, and platform support personnel.
BRD-SEC-03 (Contextual Authorization): Enforcement of Role-Based Access Control (RBAC) augmented with Relationship-Based Access Control (ReBAC) to guarantee that clinicians can only access records of patients with active appointment relationships.
BRD-SEC-04 (Encryption at Rest & Key Management): AES-256 encryption at rest for databases and blob storage; cryptographic keys managed in Azure Key Vault / AWS KMS with automated rotation.
BRD-SEC-05 (Dual-Control Privileged Access): Dual-control approval required for high-risk operations including bulk record exports, tenant migrations, and elevated support sessions.
BRD-SEC-06 (No Default Consultation Recording): Video/audio consultation streams must not be recorded by default. Any recording feature must remain disabled in MVP.
2.5 Healthcare Compliance & Governance Requirements (COM)
BRD-COM-01 (India DPDP Act 2023 Alignment): Purpose limitation, verifiable digital consent, right to correction/grievance, and strict Data Protection Impact Assessments (DPIA).
BRD-COM-02 (MoHFW Telemedicine Practice Guidelines 2020): Display of Registered Medical Practitioner (RMP) registration numbers, explicit patient consent logging, and prohibited prescribing of Schedule X drugs.
BRD-COM-03 (AI Training Prohibition): Identifiable patient clinical data and consultation metadata must never be used to train AI models without explicit, separately governed consent.
BRD-COM-04 (Emergency Care Redirection): The patient interface must prominently display notices directing acute emergencies to local physical emergency services (e.g., 112 / 108 in India).

4. User Roles, Permissions & Access Governance
The platform enforces a hybrid Role-Based Access Control (RBAC) and Relationship-Based Access Control (ReBAC) model. Workforce users are strictly isolated from patient credentials and must undergo mandatory MFA.
4.1 Persona Breakdown
Patient: Registered consumer or family member seeking medical consultations, managing bookings, submitting intake forms, attending calls, and downloading medical summaries.
Clinician (RMP): Licensed healthcare practitioner who manages availability, reviews assigned patient intake data, admits patients to video consultations, documents clinical encounters, and issues digital prescriptions.
Clinic Administrator: Operational manager responsible for provider onboarding, roster scheduling, service/fee catalog setup, resolving appointment booking exceptions, and running operational reports.
Platform Support Specialist: Technical helpdesk agent resolving account or connectivity issues. Operates under strict least-privilege: cannot view clinical notes or medical attachments.
Security & Operations Engineer (SRE): Manages cloud infrastructure, monitors system health and telemetry, rotates credentials, and responds to SEV-1–4 incidents.

6.2 RESTful API Specifications (OpenAPI Contract Summary)
Authentication & Consent Endpoints
POST /api/v1/auth/otp/request — Generates a 6-digit OTP dispatched to user's mobile. Rate limited to 3 per 10 mins.
POST /api/v1/auth/otp/verify — Validates OTP; returns short-lived JWT access token (15 mins) and refresh token (7 days).
POST /api/v1/auth/consent — Captures legal consent record with type, version, and IP.
Provider Directory & Scheduling Endpoints
GET /api/v1/providers — Query parameters: specialty, language, min_fee, max_fee, page, limit. Returns paginated clinician cards.
GET /api/v1/providers/{id}/slots — Query parameter: date=YYYY-MM-DD. Returns available time chips.
POST /api/v1/appointments/lock-slot — Acquires a 10-minute Redis distributed lock on a slot before payment.
POST /api/v1/appointments/confirm — Confirms booking after payment gateway webhook validation.
POST /api/v1/appointments/{id}/cancel — Cancels appointment; releases slot and triggers refund workflow.
Real-Time Teleconsultation Endpoints
GET /api/v1/teleconsult/{appointment_id}/token — Issues a short-lived WebRTC room access token after verifying user role and appointment state.
POST /api/v1/teleconsult/{appointment_id}/waiting-room/admit — Clinician action to admit a waiting patient into the active video bridge.
POST /api/v1/teleconsult/{appointment_id}/end — Terminates video room and updates appointment state to completed.
Clinical Encounter & Prescription Endpoints
POST /api/v1/encounters/{appointment_id}/intake — Patient submits pre-call symptoms, allergies, and vitals.
POST /api/v1/encounters/{appointment_id}/notes — Clinician documents clinical impressions and ICD-10 codes.
POST /api/v1/encounters/{appointment_id}/prescription — Clinician generates structured Rx; cryptographically hashes signature and compiles downloadable PDF.
GET /api/v1/encounters/{appointment_id}/summary — Returns patient-accessible consultation summary and downloadable signed prescription.
Document & Security Endpoints
POST /api/v1/attachments/presigned-upload — Requests a signed storage URL for upload; enforces MIME allowlist (image/jpeg, image/png, application/pdf) and 15 MB limit.
GET /api/v1/attachments/{id}/presigned-download — Generates a 15-minute expiring download URL after contextual ReBAC authorization check.

SEV-3 / SEV-4 (Minor Bugs / UI Inconvenience): Logged in ticket system; triaged in weekly sprint backlog.

Detailed Decision Profiles
Decision 01: Customer Operating Model & Tenancy Architecture [URGENT]
Options:
Option A (Recommended): Multi-tenant SaaS architecture with tenant_id column partitioning, Row-Level Security (RLS) in PostgreSQL, and tenant-scoped routing. Supports single clinics and enterprise hospital networks with zero architectural rewrites.
Option B: Single-tenant dedicated database per deployment. Simpler isolation, but significantly higher operational maintenance and cloud infrastructure cost.
Impact: Dictates database DDL, API authentication context, and administrative authorization schemas.
Decision 02: Primary Cloud Platform Selection [URGENT]
Options:
Option A (BRD Reference): Microsoft Azure (Azure Database for PostgreSQL Flexible Server, Azure Blob Storage with immutability policies, Entra External ID for CIAM, Azure Key Vault, India Central / South regions for DPDP compliance).
Option B: Amazon Web Services (AWS RDS PostgreSQL Multi-AZ, S3 with Object Lock, AWS Cognito, KMS, Mumbai/Hyderabad regions).
Impact: Freezes Terraform/Bicep landing zone automation and cloud-specific SDK bindings.
Decision 03: Real-Time WebRTC Media Provider [HIGH]
Options:
Option A (Recommended): Managed LiveKit Cloud / Open-Source SFU. Open standard, zero vendor lock-in, excellent developer ergonomics, HIPAA/SOC2 compliant, built-in adaptive simulcast.
Option B: Agora.io / Twilio Programmable Video. Mature enterprise managed services, but higher per-minute operational expense and proprietary client SDKs.
Impact: Dictates video signaling service architecture, client bundle size, and recurring monthly operating expenses.
Decision 04: Commercial Model & Payment Integration [HIGH]
Options:
Option A (Commercial Marketplace/Clinic): Mandatory upfront payment collection via Razorpay / Stripe before slot confirmation.
Option B (Assisted / Employer Health): Post-consultation billing or waived consultation fee (payment_status = 'waived_corporate').
Impact: Controls slot confirmation state machine and refund handling logic in WP5 & WP8.
Decision 05: Doctor Medical Council Credentialing Process [HIGH]
Options:
Option A (Recommended for MVP): Semi-automated document upload and internal administrative verification against State Medical Council registries before public profile activation.
Option B: Third-party credentialing API integration (e.g., National Health Authority / ABDM doctor registry).
Impact: Determines doctor onboarding turnaround time and compliance exposure under MoHFW guidelines.

11.3.1 Critical Priority Recommendations (Mandatory for Launch & Regulatory Survival)
##### Recommendation GAP-01: Family & Dependent Profile Management under Single Account
Reference Application: Practo (Patient Family Accounts), Apollo 24|7 (Family Health Profiles), eSanjeevani (Dependent OPD Tokens).
Existing BRD Coverage: Section 3.1 & 4 define a single generic "Patient" persona. The BRD assumes a 1:1 relationship between an authenticated user and the patient receiving care.
The Gap & Clinical Reality: In Indian healthcare demographics, $>65\%$ of teleconsultation bookings are made by a "Caregiver" (e.g., an adult child booking for an elderly hypertensive parent, or a mother booking for a pediatric patient). Forcing elderly patients or infants to maintain their own phone-verified accounts creates an insurmountable barrier to adoption. Furthermore, mixing medical history of multiple individuals under one account causes catastrophic clinical safety risks (e.g., mixing pediatric dosages with adult records).
Proposed Business Value: Eliminates the single largest consumer drop-off point in family healthcare; guarantees distinct longitudinal medical records per human being while sharing a primary contact and payment method.
Proposed Requirement Statement (TRM-GAP-001):
  > "The platform MUST allow an authenticated primary user to create, manage, and book appointments for multiple dependent family profiles (specifying full name, relationship, gender, date of birth, blood group, known drug allergies, and medical history). All appointments, intake questionnaires, clinical notes, and e-prescriptions MUST be bound to the specific dependent's profile ID rather than the primary account holder."
##### Recommendation GAP-02: MoHFW Statutory Drug Schedule Classification & Prohibited Drug Enforcement
Reference Application: Practo (Schedule H Verification), Apollo 24|7 (Formulary Rule Engine), eSanjeevani (Drug Master Restriction).
Existing BRD Coverage: Section 3.1 states: "prescription workflow only after clinical and jurisdictional validation." Section 9 notes general compliance with telemedicine guidelines.
The Gap & Legal Liability: The Ministry of Health and Family Welfare (MoHFW) Telemedicine Practice Guidelines (2020), Section 5 mandates strict drug scheduling rules for Registered Medical Practitioners (RMPs):
List O (Over-the-Counter): Paracetamol, ORS, antacids, vitamins, cough lozenges — permitted on any consult.
List A (First Consultation): First-line antibiotics, anti-hypertensives, oral anti-diabetics, eye drops — permitted during video consultation only.
List B (Follow-up Consultation): Add-on maintenance drugs for chronic illnesses — permitted during follow-up.
Prohibited List (Schedule X): Psychotropic and narcotic drugs under the NDPS Act (e.g., Morphine, Clonazepam, Alprazolam, Diazepam, Tramadol, Ketamine) and injectable controlled substances — strictly prohibited via telemedicine.
  Allowing a doctor to freely type and issue a Schedule X prescription exposes both the practitioner and the Kaizentrix platform to immediate criminal liability and revocation of platform operating licenses.
Proposed Business Value: Absolute statutory compliance with Indian medical law; automatic protection of platform and clinicians against narcotics violations.
Proposed Requirement Statement (TRM-GAP-002):
  > "The prescription builder MUST enforce statutory drug schedule validation against a curated Indian Pharmaceutical Formulary database. The system MUST automatically prevent the inclusion of Schedule X drugs and controlled narcotics in any digital prescription issued via teleconsultation, displaying an explicit clinical alert explaining the statutory restriction under MoHFW Telemedicine Guidelines 2020."
##### Recommendation GAP-03: Statutory Registered Medical Practitioner (RMP) Verification Badging & Public Display
Reference Application: Practo (Verified Doctor Council Badge), Apollo 24|7 (Hospital Credential Card), eSanjeevani (Government RMP Verified Seal).
Existing BRD Coverage: Section 9 states: "Validate clinician credentials, registration, specialties and permitted practice jurisdictions before enabling consultations."
The Gap: The BRD specifies backend credential validation but omits the statutory requirement to display the RMP's verified council credentials publicly to the patient before and during the consultation (MoHFW Guideline Clause 3.1.2: "The RMP should verify and display their name, qualification, and Medical Council registration number to the patient").
Proposed Business Value: Builds patient trust; fulfills mandatory legal disclosure rules; eliminates fraudulent provider claims.
Proposed Requirement Statement (TRM-GAP-003):
  > "The platform MUST publicly display the clinician's verified Full Legal Name, Medical Council Registration Number, State Medical Council of Registration, and Degree Qualifications on their public profile, booking checkout screen, in-call video header, and digitally generated e-prescription header. A verified visual badge MUST only be granted after administrative verification of medical registration certificates."
##### Recommendation GAP-04: Emergency Care Clinical Triage Rule Engine & Hard Abort Trigger
Reference Application: Apollo 24|7 (CIE Red Alert Emergency Redirection), Practo (Emergency Advisory Overlay), eSanjeevani (OPD Triage Redirection).
Existing BRD Coverage: Section 3.3 mentions: "Emergency-care replacement; the interface must direct urgent or emergency cases to appropriate local services."
The Gap: The BRD treats emergency redirection as a passive UI statement rather than an active clinical rule engine. If a patient types "crushing chest pain radiating to left arm", "unconscious infant", or "profuse arterial bleeding" into the pre-consultation intake form or search bar, the platform must not proceed to collect payment or schedule an appointment 4 hours later. Doing so represents gross clinical negligence.
Proposed Business Value: Prevents patient mortality; shields platform from malpractice litigation; enforces clinical safety best practices.
Proposed Requirement Statement (TRM-GAP-004):
  > "The pre-consultation intake form and symptom search input MUST incorporate a real-time clinical red-flag keyword evaluator (detecting acute chest pain, severe dyspnea, signs of stroke, acute trauma, poisoning, severe pediatric lethargy). Upon detection of red-flag symptoms, the booking flow MUST immediately halt, displaying a high-contrast emergency takeover modal providing direct click-to-call links to national emergency numbers (112, 108) and directions to the nearest local hospital casualty department."
##### Recommendation GAP-05: Omnichannel WhatsApp Business API Notification Integration
Reference Application: Practo (WhatsApp Appointment Reminders & Prescription Dispatch), Apollo 24|7 (End-to-End WhatsApp Care Bot).
Existing BRD Coverage: Section 3.1 & 10 specify "Notifications by email/SMS/push through approved providers".
The Gap: In India, SMS has degraded into a heavily filtered, spam-ridden channel where transactional OTPs and reminders frequently suffer delivery delays of 10–30 minutes, directly contributing to no-shows. WhatsApp is installed on $>500ext{ million}$ smartphones in India and delivers $>98\%$ open rates within 2 minutes. Missing WhatsApp severely damages the BRD's business objective of $\ge 95\%$ booking completion and reduced missed appointments.
Proposed Business Value: Reduces consultation no-show rates by $35–50\%$; allows patients to instantly access appointment join links and download signed prescription PDFs directly within their primary messaging app.
Proposed Requirement Statement (TRM-GAP-005):
  > "The notification subsystem MUST integrate with an enterprise-grade WhatsApp Business API provider (e.g., Gupshup, Infobip, Meta Cloud API) to transmit automated, templated booking confirmations, 15-minute pre-call join link reminders, rescheduling alerts, and secure prescription PDF download links, while strictly complying with privacy policies by avoiding sensitive diagnostic disclosures in the message text."
##### Recommendation GAP-06: Statutory DPDP Act 2023 Consent Manager Architecture & Data Localization
Reference Application: eSanjeevani (Sovereign Data Storage & ABDM Consent Manager), Apollo 24|7 (DPDP-ready Health Data Governance).
Existing BRD Coverage: Section 8 & 9 highlight Zero Trust, encryption, and India DPDP Act general alignment.
The Gap: The Digital Personal Data Protection (DPDP) Act, 2023 imposes statutory requirements for:
An explicit Notice and Consent Artifact separate from general Terms of Service, specifying exact data elements collected, purpose, and retention duration.
A legally mandated Consent Withdrawal Workflow that details consequences on clinical record retention (distinguishing between data that must be retained under Medical Council bylaws for 3 years vs. marketing data that must be erased).
Strict Sovereign Data Localization: all electronic medical records, video session metadata, and identifiable health tokens must reside physically within the Republic of India.
Proposed Business Value: Eliminates regulatory fines (up to ₹250 Crores under DPDP Act); positions Kaizentrix as an enterprise-grade, audit-proof platform.
Proposed Requirement Statement (TRM-GAP-006):
  > "All production databases, blob storage containers, backup archives, and application microservices MUST be physically provisioned in sovereign Indian cloud regions (e.g., Azure Central India / AWS Mumbai). The consent engine MUST issue cryptographic, tamper-proof Consent Artifacts compliant with DPDP Act standards, supporting granular consent tracking, purpose specification, and auditable consent withdrawal mechanisms."

##### Recommendation GAP-07: In-Call Real-Time Clinical Collaboration Tools (Chat, Screen Share & Camera Switch)
Reference Application: Practo (In-Call Chat & Document Viewer), Apollo 24|7 (Clinician Screen Share & Report Tray), eSanjeevani (In-Call Real-Time File Sharing).
Existing BRD Coverage: Section 3.1 covers video consultation room, waiting room, and join checks. Document sharing is described as an asynchronous upload.
The Gap: During an active video consultation, patients frequently need to present a physical lab report, show a medicine strip, or type sensitive questions. Furthermore, dermatology, ENT, and pediatric evaluations require the patient/caregiver to switch between front-facing and high-resolution rear cameras.
Proposed Business Value: Increases diagnostic confidence during remote care; prevents session abandonment caused by inability to inspect physical documents.
Proposed Requirement Statement (TRM-GAP-007):
  > "The WebRTC video consultation room MUST support: (1) an integrated in-call encrypted text chat channel for sharing dosage notes and questions, (2) clinician screen-sharing to review imaging and educational diagrams with the patient, (3) one-tap mobile camera toggle (front vs. rear) for high-resolution physical examination of dermatological lesions or physical symptoms, and (4) an in-call document drawer allowing real-time upload and immediate preview of lab reports without disconnecting the media stream."
##### Recommendation GAP-08: Standardized Clinical Terminologies (ICD-10 & SNOMED CT Auto-Suggest)
Reference Application: Apollo 24|7 (Integrated SNOMED CT / ICD-10 Search), eSanjeevani (SNOMED CT Diagnosis Picker).
Existing BRD Coverage: Section 3.2 defers standardized clinical coding to a later phase. Section 7 lists icd10_codes in the logical data model without operational requirements.
The Gap: Free-text clinical notes prevent automated clinical audit, impede epidemiological reporting, and prevent future interoperability with hospital EHRs and ABDM. Manual entry of diagnostic codes is tedious; clinicians require an auto-complete search engine mapped to standard clinical vocabularies.
Proposed Business Value: Eliminates medical transcription ambiguity; prepares platform for ABDM Milestone 2 compliance with zero technical debt; standardizes clinical quality across clinics.
Proposed Requirement Statement (TRM-GAP-008):
  > "The clinician charting interface MUST incorporate a high-speed auto-complete search component linked to standard ICD-10-CM and SNOMED CT clinical terminology databases. Clinicians MUST be able to search diagnoses using common clinical synonyms (e.g., typing 'high BP' suggests 'Essential (primary) hypertension - ICD-10 I10'), binding standardized codes directly to the clinical encounter record."
##### Recommendation GAP-09: Complimentary 7-Day Follow-Up Workflow & Query Grace Period
Reference Application: Practo (7-Day Free Follow-Up Window), Apollo 24|7 (Complimentary Doctor Query Window), eSanjeevani (Revisit Token Mechanism).
Existing BRD Coverage: Section 1 & 4 mention "manage follow-up care" and "receive approved summary/follow-up".
The Gap: In Indian clinical outpatient practice, an initial consultation often requires the patient to undergo diagnostic blood tests or start medications and return to show reports within 3–7 days. Forcing patients to pay a full consultation fee just to show routine lab results causes immense friction and negative reviews. The BRD lacks rules governing follow-up validity, free query windows, and doctor response SLAs.
Proposed Business Value: Aligns with standard Indian medical practice; dramatically enhances patient retention and CSAT scores; formalizes doctor liability during post-call queries.
Proposed Requirement Statement (TRM-GAP-009):
  > "The scheduling and consultation engine MUST support a configurable 'Follow-Up Policy' (defaulting to 7 calendar days post-consultation). Within this window, the patient MUST be entitled to: (1) send asynchronous follow-up text messages and lab test attachments to the attending clinician, and/or (2) book one complimentary follow-up video review if designated as 'Review Required' by the clinician, automatically waiving consultation fees."
##### Recommendation GAP-10: Clinic Front Desk / Receptionist / Triage Nurse Role & Delegation
Reference Application: Practo (Practo Ray Front Desk Staff Role), Apollo 24|7 (MedSys Triage Nurse Interface), eSanjeevani (CHO Spoke Screening Role).
Existing BRD Coverage: Section 4 defines: Patient, Clinician, Clinic Administrator, Platform Support, Security/Operations.
The Gap: In private clinics, polyclinics, and hospital OPDs, doctors never register walk-ins, update cash receipts, or input baseline patient vitals themselves; clinic administrators do not perform daily clinical desk duties. These tasks are performed by Front Desk Receptionists and Triage Nurses. Omitting this persona forces clinicians to do clerical data entry, causing severe operational bottlenecks.
Proposed Business Value: Enables adoption in real-world outpatient clinics and enterprise hospital departments; accelerates doctor consultation turnaround time.
Proposed Requirement Statement (TRM-GAP-010):
  > "The platform MUST introduce a dedicated 'Front Desk / Triage Staff' role. Users with this role MUST have scoped permissions within their assigned clinic to: (1) register walk-in patients, (2) capture preliminary vital signs (BP, Pulse, SpO2, Temperature, Weight) into the patient intake record, (3) verify patient arrival and check patients into the clinician's live queue, and (4) collect offline cash/card payments and print billing vouchers."
##### Recommendation GAP-11: Clinician Practice Productivity Tools (Clinical Macros & Prescription Templates)
Reference Application: Practo Pro (Quick Rx Templates & Frequency Chips), Apollo Clinician (Standard Treatment Order Sets).
Existing BRD Coverage: Section 3.1 & 7 outline consultation notes, structured summary, and prescription builder.
The Gap: Typing repetitive drug names, dosages (e.g., "Tab. Amoxicillin + Clavulanic Acid 625mg, 1 tablet twice daily after food for 5 days"), and standard post-consultation lifestyle advice for every single patient takes 5–8 minutes per encounter. Practo Pro and Apollo Clinician achieve rapid charting (<90 seconds) using one-click clinical templates and macros.
Proposed Business Value: Cuts clinician charting time by $>60\%$; dramatically reduces doctor cognitive fatigue; ensures zero prescription entry errors.
Proposed Requirement Statement (TRM-GAP-011):
  > "The clinician workspace MUST provide customizable 'Prescription Templates' and 'Clinical Order Sets' allowing doctors to create and save frequent diagnosis clusters (e.g., 'Acute Upper Respiratory Infection', 'Type 2 Diabetes Routine Refill'). Applying a template MUST populate the diagnosis, standard medication regimen, dosage frequency, and patient lifestyle instructions in a single tap, with full clinician ability to edit prior to digital sign-off."
##### Recommendation GAP-12: Provider Financial Settlements, Commission Splits & Indian Tax Accounting (TDS / GST)
Reference Application: Practo (Automated Doctor Payouts & Section 194J TDS Deduction), Apollo 24|7 (Physician Revenue Reconciliation).
Existing BRD Coverage: Section 3.1 & 10 address patient payment collection, payment gateway tokenization, and customer refunds.
The Gap: Teleconsultation platforms operate as electronic commerce operators. When a patient pays ₹1,000 for a consultation:
The platform must split this into Clinic/Doctor Payout (e.g., 80% = ₹800) and Platform Convenience/Service Fee (e.g., 20% = ₹200).
Indian tax law requires deducting Tax Deducted at Source (TDS) under Section 194J (professional fees) or Section 194-O (e-commerce marketplace).
The platform must generate compliant GST Invoices for the service fee.
  The BRD has zero provisions for doctor bank account verification, automated payout settlements (e.g., T+2 days via Razorpay Route / Stripe Connect), or withholding tax accounting.
Proposed Business Value: Prevents tax non-compliance penalties; eliminates manual accounting chaos; provides transparent earnings statements for participating doctors.
Proposed Requirement Statement (TRM-GAP-012):
  > "The financial subsystem MUST implement automated provider payout splitting and ledger accounting. The system MUST: (1) verify provider bank account credentials via penny-drop validation, (2) compute platform commission and provider net proceeds per consultation, (3) calculate and withhold statutory Indian TDS under Section 194J/194-O, (4) disburse net earnings on a defined settlement schedule (T+2/T+7), and (5) generate automated GST-compliant tax invoices for platform service fees."

Supporting ABDM Milestone 1 (M1) (allowing patients to authenticate using their 14-digit ABHA number or create a new ABHA via Aadhaar OTP) is becoming a prerequisite for institutional hospital contracts and government clinic pilots.
Proposed Business Value: Unlocks institutional enterprise contracts with hospital chains participating in Ayushman Bharat; provides seamless patient identity resolution across disparate clinics.
Proposed Requirement Statement (TRM-GAP-013):
  > "The identity subsystem MUST incorporate ABDM Milestone 1 (M1) interfaces, allowing patients to create an ABHA ID via Aadhaar/Mobile OTP, search for their existing ABHA number, and link their ABHA address (@abdm) to their platform profile, storing verified ABHA tokens in compliance with National Health Authority (NHA) security guidelines."
##### Recommendation GAP-14: Geo-Location Radius Search & Clinic Physical Map Navigation
Reference Application: Practo (Doctor Search by Distance Radius & Google Maps Pin), Apollo 24|7 (Nearby Hospital Locator).
Existing BRD Coverage: Section 3.1 & 4 define provider search by specialty, clinic, language, availability, and fee.
The Gap: Even in a teleconsultation platform, patients frequently choose doctors based on proximity (e.g., "Cardiologist within 5 km"), anticipating that if physical examination or emergency hospitalization is required, they can easily visit the doctor's physical clinic. The BRD directory lacks geospatial distance filtering and physical clinic address mapping.
Proposed Business Value: Increases patient booking confidence by connecting them with local clinicians; bridges online teleconsultation with physical offline care continuity.
Proposed Requirement Statement (TRM-GAP-014):
  > "The provider directory MUST incorporate geospatial indexing (PostGIS / spatial queries), allowing patients to filter clinicians by distance radius (e.g., within 5 km, 10 km, 25 km of current GPS location or selected postal code). Provider profile and booking confirmation views MUST display the physical clinic address integrated with interactive maps (e.g., Google Maps / MapmyIndia) providing one-tap driving directions."
##### Recommendation GAP-15: Verified Patient Reviews, Ratings & Content Moderation Workflow
Reference Application: Practo (Verified Patient Stories & Doctor Feedback Moderation), Apollo 24|7 (Post-Consultation Star Ratings).
Existing BRD Coverage: Section 2 mentions measuring patient experience via post-consultation surveys to baseline CSAT/NPS.
The Gap: The BRD uses post-consultation surveys exclusively for internal operational metrics. In modern digital healthcare, $>80\%$ of consumers select providers based on public verified patient ratings and feedback. Without a transparent review engine, patients default to searching external platforms (Google Reviews, Practo) to evaluate doctors.
Proposed Business Value: Drives marketplace liquidity; rewards high-performing clinicians; provides social proof that elevates platform booking conversion rates.
Proposed Requirement Statement (TRM-GAP-015):
  > "The platform MUST implement a 'Verified Patient Feedback' subsystem. Only patients who have completed a paid consultation with a clinician MUST be permitted to submit a star rating (1 to 5) and qualitative review across standardized parameters (Bedside Manner, Explanation of Illness, Wait Time). The system MUST include an automated moderation queue to filter profanity or defamatory language and permit clinicians to post a professional public reply."
##### Recommendation GAP-16: Instant On-Demand Teleconsultation Pool Matching (<15-Minute SLA)
Reference Application: Practo Consult (2-Minute Instant General Physician Matching), Apollo 24|7 (Express 15-Minute Consultation), eSanjeevani (Live OPD Token Queue).
Existing BRD Coverage: Section 3.1 & 4 focus strictly on pre-scheduled appointment slots.

However, acute illnesses (e.g., sudden midnight fever, acute pediatric vomiting, migraine) require immediate medical consultation. In Practo and Apollo, instant on-demand consultations account for $>40\%$ of total teleconsultation transaction volume.
Proposed Business Value: Unlocks an enormous segment of high-intent, high-urgency patients; drives platform revenue during non-business hours and weekends.
Proposed Requirement Statement (TRM-GAP-016):

Patients seeking urgent medical advice MUST be able to enter a dynamic triage queue that broadcasts the consultation request to a pooled roster of currently 'Online & Active' General Physicians. The first responding clinician accepts the session, establishing a WebRTC video room within a guaranteed SLA of $\le 15ext{ minutes}$."

All core patient-facing journeys (discovery, booking, intake, waiting room, video controls, and post-call instructions) MUST feature localized string bundles and accessible Indic typography."

To ensure prescriptions and diagnostic records are interoperable worldwide, the clinical database schema stores dual coding:
Primary Care Diagnoses: Encoded in ICD-10-CM (globally recognized) and mapped to SNOMED CT.
Medications: Configured with a localized coding mapper:
In India: Mapped to CDSCO National Drug Master.
In the United States: Mapped to RxNorm (National Library of Medicine concept codes) for Surescripts routing.
In the United Kingdom: Mapped to dm+d (Dictionary of Medicines and Devices) for NHS EPS routing.
In France: Mapped to CIP/UCD codes for SESAM-Vitale billing.
In Germany: Mapped to PZN (Pharmazentralnummer) for e-Rezept routing.
3. Standardized HL7 FHIR R4 Interoperability Profiles
The integration layer implements a standardized FHIR R4 Facade supporting:
Patient (harmonized across ABDM ABHA profile, US Core Patient, and UK Core Patient).
Encounter (recording teleconsultation metadata, start/end timestamps, and provider NPI / GMC / Council ID).
Condition (clinical diagnoses bound to ICD-10 and SNOMED CT).
MedicationRequest (structured prescriptions compliant with FHIR e-prescribing standards).
DocumentReference (PDF consultation summaries and lab reports with cryptographic SHA-256 hashes).

F04: Multi-Party Clinical Call
Doctor + Patient in call -> Doctor invites remote family caregiver.
Unauthorized third party intercepts room link and attempts to join clinical call.

F05: Asynchronous Photo Intake
Patient captures skin rash photo -> Uploads during intake form.
Patient attempts to upload an executable malware script disguised as a .jpg or an oversized 45 MB image.

Patient waitlisted -> Earlier slot cancels -> Notification sent -> Claimed.
Three waitlisted patients tap the WhatsApp notification link simultaneously to claim the single open slot.

ADR-03: Primary Database, Distributed Cache & Concurrency Control
Status: APPROVED & FINALIZED
Context: The platform requires rock-solid ACID transactional integrity for financial checkout and appointment booking, sub-millisecond distributed locks to prevent slot double-booking, and flexible storage for semi-structured clinical intake forms and vitals.
Options Evaluated:
Option A (Recommended): Managed PostgreSQL 16 (Relational ACID + PostGIS + JSONB) + Redis 7 Cluster (Redlock Engine).
Option B: MongoDB 7.0 (Document Store) + Redis.
Option C: MySQL 8.0 + Memcached.
Decision Rationale:
PostgreSQL 16 provides the gold standard for relational healthcare data:
Multi-Tenancy Security: Built-in Row-Level Security (RLS) enforces strict logical tenant isolation at the database kernel level, guaranteeing that Clinic A can never access Clinic B's records.
Geospatial Capabilities: PostGIS extension enables high-speed spatial distance queries (ST_DWithin) for doctor distance radius filtering.
Semi-Structured Clinical Flexibility: JSONB columns allow patient intake forms, vitals snapshots, and dynamic questionnaire responses to be stored and indexed with GIN without frequent DDL schema migrations.
Redis 7 Cluster implements the Redlock distributed locking algorithm, guaranteeing that when concurrent requests target the same doctor slot, exactly one request acquires an atomic 10-minute reservation mutex, completely eliminating double-bookings.

16.3 Detailed Specifications for Core Services (Services 1 to 7)
1. Identity, Auth & Profile Service (`auth_service`)
Primary Responsibilities: Mobile phone SMS OTP authentication, Entra ID OIDC token exchange, clinician TOTP MFA verification, RBAC authorization, and user profile management.
Concurrency & Security Invariants:
Strict rate limiting: Maximum 5 OTP requests per 15 minutes per phone/IP.
OTP generation uses cryptographically secure PRNG (secrets.choice(string.digits)); 6-digit code with 300-second TTL in Redis.
Failed OTP verification counter stored in Redis; locks credential after 5 consecutive incorrect attempts.
Internal API Contracts:
POST /api/v1/auth/otp/send: Generates and dispatches SMS OTP via Gupshup adapter.
POST /api/v1/auth/otp/verify: Validates OTP against Redis cache and mints RS256 JWT access token (60-min expiry) + refresh token (7-day sliding window).
POST /api/v1/auth/mfa/totp/verify: Validates RFC 6238 TOTP code for clinical/admin users before elevating session privileges.
Published Events: user.registered, user.authenticated, user.mfa_enrolled, user.account_locked.
2. Appointment & Slot Management Service (`appointment_service`)
Primary Responsibilities: Clinician schedule roster indexing, slot availability searching, distributed concurrency lock orchestration via Redis Redlock, instant tele-triage queue management, and booking state transition tracking.
Concurrency & Race Condition Prevention:
Enforces Redlock Distributed Mutex across Redis cluster nodes with a strict 600,000 ms (10-minute) TTL:
    `python
    key = f"resource:slot_lock:{slot_id}"
    acquired = await redis_client.set(key, user_id, nx=True, px=600000)
    if not acquired:
        raise SlotAlreadyReservedException("This slot is currently held by another patient.")
    
Zero double-booking guarantee: The database schema enforces a unique partial index on (doctor_id, start_time) for non-cancelled appointments.
Internal API Contracts:
GET /api/v1/appointments/slots: Returns available consultation slots filtered by doctor, specialty, date, and geo-radius (PostGIS).
POST /api/v1/appointments/lock: Acquires Redis distributed mutex and creates an ephemeral reservation record.
POST /api/v1/appointments/confirm: Transitions reservation to CONFIRMED upon receiving verified payment capture event.
POST /api/v1/appointments/cancel: Cancels booking, releases mutex, and enqueues refund task.
Published Events: appointment.locked, appointment.confirmed, appointment.cancelled, appointment.no_show.
3. Teleconsultation & Media Orchestration Service (`consultation_service`)
Primary Responsibilities: LiveKit WebRTC room lifecycle management, participant token minting, doctor/patient online presence tracking, in-call clinical SOAP notes capture, ICD-10 codification, and session duration auditing.
Concurrency & Media Invariants:
LiveKit JWT access tokens minted with explicit participant identity, room name, and granular permissions (can_publish, can_subscribe, can_publish_data).
Room automatically provisioned when doctor or patient enters waiting room; automatically terminated when doctor concludes consultation or after 60 minutes of inactivity.
Presence heartbeat: Clients emit WebSocket ping every 10 seconds; Redis tracks active presence keys with 25-second expiry.
Internal API Contracts:
POST /api/v1/consultations/start: Initializes clinical consultation session and provisions LiveKit room.
GET /api/v1/consultations/{id}/token: Generates short-lived LiveKit JWT access token for authorized participant.
PUT /api/v1/consultations/{id}/notes: Saves structured clinical SOAP notes (Subjective, Objective, Assessment, Plan) with ICD-10 diagnostic codes.
POST /api/v1/consultations/{id}/conclude: Finalizes encounter, records statutory duration, and unlocks prescription authoring.
Published Events: consultation.room_ready, consultation.participant_joined, consultation.ended, consultation.quality_degraded.
4. Electronic Prescription & Clinical Order Service (`prescription_service`)
Primary Responsibilities: Formulation formatting per MoHFW Telemedicine Guidelines 2020, doctor digital signature (RSA-2048 / PKI) generation via Azure Key Vault, asynchronous PDF rendering (WeasyPrint), and statutory WORM storage upload.
Statutory Compliance & Invariants:
Mandatory prescription header fields: Doctor Name, Medical Council Registration Number (NMC/SMC), Clinic Address, Patient Demographics, Chief Complaints, Diagnosis, Medication Table (Generic name, Dosage form, Strength, Frequency, Duration, Instructions).
Immutability guarantee: Once a prescription is digitally signed, its cryptographic hash (SHA-256) is committed to the database and can never be updated or overwritten. Any correction requires issuing an explicit Addendum.
Internal API Contracts:
POST /api/v1/prescriptions: Accepts prescription payload from doctor, validates generic formulations, and acquires digital signature.
GET /api/v1/prescriptions/{id}: Returns structured prescription details with verified signature status.
GET /api/v1/prescriptions/{id}/pdf: Returns secure, time-limited Azure Blob Storage SAS URI for downloading the signed PDF.
Published Events: prescription.created, prescription.signed, prescription.pdf_rendered, prescription.dispatched.
5. Payment & Settlement Service (`payment_service`)
Primary Responsibilities: Razorpay order generation, UPI Intent payment capture, webhook signature verification (X-Razorpay-Signature), Section 194J / 194-O TDS withholding calculation, and automated doctor payout ledger accounting.
Idempotency & Financial Invariants:
All webhook events must be validated using HMAC-SHA256 with the configured secret.
Deduplication: Webhook event_id is recorded in processed_webhook_events table within a serializable database transaction; duplicate webhooks immediately return HTTP 200 without reprocessing.
Statutory TDS calculation: For participating private doctors, platform automatically calculates 10% Section 194J TDS and splits balance into escrow sub-accounts via Razorpay Route:
    $$ext{Payout Amount} = ext{Consultation Fee} - ext{Platform Fee} - (ext{Consultation Fee} imes 0.10)$$
Internal API Contracts:
POST /api/v1/payments/create-order: Generates Razorpay order with linked booking metadata.
POST /api/v1/payments/webhook: Ingests and validates asynchronous payment gateway callbacks.
POST /api/v1/payments/refund: Triggers automated refund to patient for doctor-cancelled sessions.
Published Events: payment.created, payment.captured, payment.failed, payout.escrowed, payout.settled.
6. Interoperability & ABDM Gateway Service (`abdm_service`)
Primary Responsibilities: Ayushman Bharat Digital Mission (ABDM) Milestone 1 (ABHA creation/verification), Milestone 2 (HIP/HIU health data linking), and Milestone 3 (FHIR R4 Bundle exchange via National Consent Manager).
ABDM Security & Protocol Invariants:
Outbound requests to ABDM Gateway sign payloads using RSA-2048 private key; mutual TLS (mTLS) with NHA client certificate.
Incoming health information requests verified against signed ABDM Consent Artifact; requests rejected if consent is expired, revoked, or requested data scope exceeds consent permissions.
All clinical records serialized into compliant HL7 FHIR R4 Bundles (Bundle.type = "document" containing Composition, Patient, Practitioner, Encounter, Condition, MedicationRequest).
Internal API Contracts:
POST /api/v1/abdm/abha/generate: Initiates Aadhaar / Mobile OTP flow for ABHA address creation.
POST /api/v1/abdm/consent/verify: Validates NHA consent artifact for medical records transfer.
POST /api/v1/abdm/fhir/bundle: Generates and validates HL7 FHIR R4 JSON document for a completed teleconsultation.
Published Events: abdm.abha_linked, abdm.consent_granted, abdm.records_pushed.
7. Omnichannel Notification & Messaging Service (`notification_service`)
Primary Responsibilities: Template hydration, delivery prioritization, Gupshup WhatsApp Business API integration, TRAI DLT transactional SMS dispatch, and web push notifications.
Privacy & Delivery Invariants:
Out-of-band notifications must never contain Protected Health Information (PHI), medical diagnoses, or prescription drug names.
Messages contain secure, single-use, time-limited magic links (https://app.kaizentrix.com/v/{token}) requiring biometric or OTP verification.
Internal API Contracts:
POST /api/v1/notifications/dispatch: Enqueues an out-of-band notification job across configured channels.
POST /api/v1/notifications/webhook/gupshup: Ingests message delivery receipts (Delivered, Read, Failed) to maintain telemetry.
Published Events: notification.dispatched, notification.delivered, notification.failed.

17.3 Concurrency Control & Zero Double-Booking Partial Unique Indexing
To mathematically guarantee zero double-booking under extreme concurrency spikes (such as morning booking rushes or viral campaign traffic), the database schema deploys a partial unique index:
-- Partial Unique Index on Doctor Schedule Slots-- Prevents overlapping active reservations or confirmed bookings for the same doctorCREATE UNIQUE INDEX uq_doctor_slot_active ON clinical.appointment_slots (doctor_id, start_time) WHERE status NOT IN ('CANCELLED');-- Index on Ephemeral Slot Locks for Fast Lock Expiry SweepingCREATE INDEX idx_slot_locks_activeON clinical.appointment_slots (lock_expires_at)WHERE status = 'RESERVED';
Defense-in-Depth Concurrency Model:
Tier 1 (In-Memory Mutex): Redis 7 Redlock acquires a distributed 10-minute lock in $< 2$ ms. If another user attempts to reserve the same slot_id, Redis immediately rejects the request.
Tier 2 (Database Engine Safety Net): If an edge race condition ever bypasses the cache, PostgreSQL evaluates the uq_doctor_slot_active index inside a serializable transaction. If two concurrent transactions attempt to book the slot, PostgreSQL terminates the second transaction with error code 23505 (unique_violation). Double-booking is physically impossible at the storage engine level.
17.4 Row-Level Security (RLS) & Multi-Tenant Data Isolation Policies
To comply with the Digital Personal Data Protection (DPDP) Act, 2023 and HIPAA Security Rules, PostgreSQL Row-Level Security (RLS) is enabled across all sensitive clinical and appointment tables. Every database query executed by the application backend must declare the executing user's tenant context:
-- Enable and Force Row-Level Security on Appointments and EncountersALTER TABLE clinical.appointments ENABLE ROW LEVEL SECURITY;ALTER TABLE clinical.appointments FORCE ROW LEVEL SECURITY;ALTER TABLE clinical.consultation_encounters ENABLE ROW LEVEL SECURITY;ALTER TABLE clinical.consultation_encounters FORCE ROW LEVEL SECURITY;ALTER TABLE clinical.prescriptions ENABLE ROW LEVEL SECURITY;ALTER TABLE clinical.prescriptions FORCE ROW LEVEL SECURITY;-- ------------------------------------------------------------------------------ RLS Isolation Policy: Appointments Table-- ------------------------------------------------------------------------------ 1. Patients can ONLY see their own appointment recordsCREATE POLICY patient_appointment_isolation ON clinical.appointments    FOR ALL    TO application_role    USING (        patient_id IN (            SELECT id FROM core.patient_profiles             WHERE user_id = NULLIF(current_setting('app.current_user_id', true), '')::UUID        )    );-- 2. Clinicians can ONLY see appointments assigned to their profileCREATE POLICY doctor_appointment_isolation ON clinical.appointments    FOR ALL    TO application_role    USING (        doctor_id IN (            SELECT id FROM core.doctor_profiles             WHERE user_id = NULLIF(current_setting('app.current_user_id', true), '')::UUID        )    );-- 3. 17.6 Database Migration Framework & Zero-Downtime Migration Strategy
To support continuous deployment without scheduled maintenance downtime, database schema evolution is managed via Alembic utilizing the Expand-Contract Migration Pattern:

Key Alembic Engineering Guidelines:
Never rename columns directly: Rerouting column names causes immediate application crashes during canary deployments; follow the Expand-Contract pattern.
Always create indexes concurrently: In production, write op.create_index(..., postgresql_concurrently=True) to prevent table locks on active clinical booking tables.
Strict transaction timeouts: Every migration sets SET statement_timeout = '15s' to prevent schema changes from waiting indefinitely on active locks.
